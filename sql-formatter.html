What does this SQL Formatter do?


This free online SQL formatter — also called a SQL beautifier or SQL pretty printer — takes compact, poorly indented or copy-pasted SQL and rewrites it with consistent indentation, spacing and line breaks so it is readable and editable. Major clauses like SELECT, FROM and WHERE get their own lines, column lists are indented, and joins and subqueries are aligned so the structure of the query is obvious at a glance.


The same tool works in reverse. Switch to SQL minifier mode and it collapses your query into the most compact safe form, removing extra whitespace and comments. That is exactly what you want when you're storing queries as strings inside application code, config files or test fixtures.


Everything runs locally in your browser. The SQL you paste never leaves your device, there is no signup, and there are no usage limits. Format or minify as many queries as you want, as many times as you want, for personal or professional projects.

SQL beautify vs. SQL minify — what is the difference?


These two operations are opposites, and this tool does both.






ModeWhat it doesBest forTypical size change



Beautify / FormatAdds indentation, line breaks and clause breaks. Expands compact SQL into a readable structure.Development, debugging, code review, learningIncreases size (adds whitespace)


MinifyRemoves whitespace and comments. Collapses the query into the smallest safe form.Storing queries in source code, config files, test fixtures20–50% smaller







If you have readable SQL and need to compact it — for example to embed in a JavaScript string or a YAML config — use Minify SQL. If you have a wall of SQL and need to understand it, use Beautify SQL.







SQL formatting best practices


Whatever style you choose, keep it consistent across your team. Here are the conventions most teams follow:


    

  • Uppercase SQL keywords. Makes keywords stand out against identifiers and strings.
    • 

  • One clause per line. SELECT, FROM, WHERE, GROUP BY etc. each start on their own line.
    • 

  • One column per line. A long SELECT list is easier to scan vertically than horizontally.
    • 

  • Indent subqueries and CTEs. Nesting should be visible at a glance — the deeper you go, the more indent.
    • 

  • Lead with AND / OR. In a WHERE clause, put the operator at the start of the line so a reviewer can count conditions easily.
    • 

  • Group JOINs under FROM. Every JOIN at the same indent level as FROM, with its ON condition indented below.
    • 

  • Align column aliases. Optional but makes wide SELECT lists more readable (u.id AS user_id).
    • 

  • Use comments for intent, not mechanics. Explain why a filter is there, not what the syntax does.
    • 

  • Keep lines under ~100 characters. Wrap long expressions with parentheses and indentation.
    • 

  • Run the formatter before committing. A consistent diff is easier to review than one that mixes styles.
